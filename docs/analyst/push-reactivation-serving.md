# Serving reactivation recommendations

This is a proposed design for the first meme delivered to a dormant user. Training and evaluation run on the analyst computer. A small worker would score candidates ahead of each existing broadcast. Product approval for a shadow run and a subsequent randomized test are separate decisions.

## One scheduled opportunity

1. Keep the existing cadence and send/holdout assignment. Select the eligible user batch first. In particular, the monthly audience uses the product's stored last reaction and blocking rules. Offline estimates condition on a delivered meme and a reconstructed idle interval. Measure how often the two eligibility definitions disagree.
2. Prepare a bounded pool for each language in advance. Include currently allowed media, existing HQ quality floors and more than one source. Build pools with a scheduled batch query or refresh changed memes from an existing stats job. Read immutable pool versions in the worker. A larger SQL LIMIT on the current per-user HQ sort still incurs the sort. Benchmark pool construction independently. Check how often each language and dormancy group runs out of unseen eligible options.
3. At batch time assemble up to 32 eligible candidates per user from these pools. Use a set-based lookup of seen user/meme pairs with the unique index, in bounded batches of e.g. 100 recipients. Page once more within a fixed scan budget if the first pool is exhausted. Bound work by recipients × candidate/lookahead cap. Join feature tables once per batch. A candidate should not trigger a query.
4. Read a versioned model once per worker. Validate schema, transforms, finite coefficients, positive scales and supported version before use. Compute each candidate's probability in memory and use a deterministic tie break. Retain its top alternatives and expiry with the opportunity. With additive logistic regression, common user terms cancel when ranking the same user's candidates. Source affinity and meme features change their relative order.
5. Immediately before the scheduled send, recheck consent/block state, language, cadence, recent activity, meme moderation/media status and unseen status. Try the next still-valid cached candidate within the cap. If a batch/model artifact is unavailable, expired or invalid, use the normal picker once under the existing capacity budget. Recheck the scheduled opportunity before any fallback. For overloaded workers, disabling the challenger returns the system to the existing picker.

## Feature costs and parity

| Input | Batch work and serving contract |
|---|---|
| Meme and source | Aggregate feed sends, valid callbacks and likes over the preceding 35 days using past timestamps. Keep daily buckets with boundary adjustments or prepare an exact timestamped snapshot. Preserve product exclusions and Beta(1,1) smoothing. Current lifetime stats and their smoothing have different semantics. |
| User | For the users in the upcoming batch, precompute the last valid callback, previous push and 35-day counts. A past push enters the response rate only after its 24-hour window. Update recent activity before dispatch. |
| User and source | Fetch each eligible user's last 200 genuine feed callbacks within 365 days **across all sources**; group that bounded sequence by source. Maintain 35-day recent affinity separately. Reuse results for all candidates for this user. Store a count of zero and a smoothed rate of 0.5 for observed empty history. Keep missing features distinct. |
| Clock and model | Compute ages from timestamps with a consistent UTC decision clock. Store feature version, watermark and maximum lag in each artifact. On sampled shadow decisions replay the feature computation at that watermark and compare feature values, probabilities and top choices. Also quantify the change due to lag from the actual decision time. Set expiry from measured lag and disagreement. |

The index on user and reaction time and the unique user/meme index support bounded batch lookups. A top-200 query can inspect more than 200 underlying rows when many callbacks fail feed filters. Budget elapsed time, rows visited and buffers. Run analytical exports serially on a replica or existing restored copy when available. A read-only connection to the primary still consumes CPU and I/O. Reuse a private, immutable local snapshot across all training trials. A future routine export should retrieve only the necessary evaluation window when scoring frozen weights. Snapshots made with different salts cannot be concatenated for user-level retraining. A full bounded training refresh or a separately designed stable pseudonym is required for that use.

## Delivery and measurement

The current direct sender can return after an internally handled Forbidden, while the outer broadcast counts a send. Monthly Redis membership is checked before send and updated after. A crash or parallel invocation between those operations makes the counters and deduplication insufficient for an online experiment.

Before any experimental dispatch, reserve a unique **user + campaign + scheduled occurrence** and stable user-level arm in durable storage. Record the chosen meme, arm, model/pool/feature versions and probability of selection before sending. A policy change must reuse the same reservation. Capture Telegram acceptance with its message ID, definite failure, or ambiguous network outcome. An ambiguous attempt is quarantined for reconciliation. Telegram does not provide an application idempotency key for this call, so blind replay can duplicate a push. Offline training uses accepted deliveries; the experiment uses everyone assigned.

- **Shadow.** Observe the existing live pick when it actually runs. The shadow side reads cached candidates without popping or refilling the live feed queue. Log top-K, eligibility failures, empty pools, overlap with the actual pick, score range, source coverage, lookup latency, precompute wall time and fallback. A different pool changes both retrieval and ranking; a future test against the existing HQ path will estimate their combined effect.
- **Capacity.** Start with one shadow batch in one supported cadence step. Establish current query count, p95/p99 pick latency, database buffers, worker CPU and queue lag. As proposed budgets, cap each batch at 100 users and 32 scored candidates per user, keep p95 additional worker scoring below 5 ms per user and p95 end-to-end picker latency within 10% of the baseline. Measure both on the target host. Pause shadow on timeouts, worsening queue lag or repeated budget violations. Synthetic laptop timings cover only arithmetic.
- **Content experiment.** Preserve the current silent holdout. Within one existing sending step, randomize eligible users once between existing HQ and challenger. Count the first eligible assignment per user for the primary readout. Include skipped, uncertain and failed deliveries in the assigned denominator. Primary outcome is a stored callback on the assigned meme within 24 hours. Report downstream feed callbacks on days 7–14, recorded block detection, deliveries and ambiguous outcomes by arm. Keep the post-return feed identical across arms. Power the test from eligible users, observed disagreement and a chosen absolute effect; there is no universal overlap threshold.
- **Decision.** Register dates, minimum detectable effect, acceptable block/delivery harm and stopping rule before launch. If a prespecified harm boundary fires or dispatch bookkeeping fails, disable the challenger and inspect the affected batch. Do not promote a model based on offline log loss, AUC or a single favorable temporal fold. Testing whether to send at all or delay a send is a different randomized comparison.
